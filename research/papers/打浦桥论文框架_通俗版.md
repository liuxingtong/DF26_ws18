# 打浦桥论文框架：让不同主体的需求进入可修改的城市方案

依据：C6、R22、R23、R28、R30 及前期文献调研；2026-09-14 对当前源码的核查。下文是研究与开发建议，不是已经完成的功能或实验结果。本轮没有修改业务代码，也未重跑整个打浦桥流程；只对高度分配函数做了一个人工构造的小例子检查。

## 一、这类论文通常怎么讲故事

这些论文并没有完全相同的方法，但可以归纳出共同的写作思路：

**现实中有一个具体困难 → 现有工具在哪一步帮不上忙 → 提出一种新的操作流程 → 做出工具 → 在真实场地或明确任务中试用 → 说明解决了什么、还有什么做不到。**

| 论文 | 问题从哪里来 | 它主要补哪一步 | 对我们的启发 |
|---|---|---|---|
| C6 | 公众难以理解更新影响，也难以影响选择 | 提案、反方案、共同选择；情境化三维浏览 | 把参与安排讲清楚，让人能比较并提出替代方案 |
| R22 | 城市数字孪生能展示数据，却不充分支持设计 | 把城市上下文与生成式设计连接起来 | 现状模型要能支持修改和重新计算 |
| R23 | 用户要求难以变成适应真实场地的布局 | 把边界、已有要素与偏好写成硬软约束 | 每条需求要有明确的空间含义和执行条件 |
| R28 | 收集到大量意见后，难以整理和分析 | 公众反馈的处理、分析和可视化 | 收集意见之后还要解释它们、检查遗漏并返回给用户 |
| R30 | 通用数字工具容易丢掉具体地点的生活经验 | 把现场参与获得的知识带回数字工具 | 让意见能绑定到具体地点，允许用户补充预设选项之外的情况 |

这张表是综合理解，不能写成每篇论文都实现了完整流程。C6 主要验证浏览原型；R23 承认逐轮生成交互有限；R28 是数据分析工具；R30 包含现场活动和教学原型。R22、R28 本轮依据主要是已核实摘要与正文片段，不能据此推断其完整技术细节。

## 二、我们的文章可以集中回答什么

**在整个打浦桥街道范围内，怎样让居民、开发者和政府表达不同的更新要求，把这些要求变成有依据的空间修改，并看清不同方案让谁受益、让谁承担代价？**

建议用“居住空间保留、开发容量和公共空间改善之间的取舍”作为贯穿全文的任务。研究范围仍是整个打浦桥，不缩成一条弄堂。不同位置可以采用不同更新方式；局部例子用于解释规则，全区数据用于检查影响。

参与主体继续使用 resident、developer、state 三类。设计师或研究人员可以协助使用工具，不必因此增加一个利益主体。unknown 表示资料不足，不是第四个参与群体；代码中保留的 informal 没有当前数据支持，不应生成虚构参与结果。

“整个打浦桥街道”也不意味着范围内所有建筑都属于历史保护对象。应在同一范围内区分已核实的保护对象、一般既有建筑、可能更新的地块与资料不足区域。

## 三、适合我们的完整工作流程

**建立打浦桥现状 → 收集三类主体的要求 → 把要求变成明确规则 → 修改空间并检查 → 比较全区与局部影响 → 参与者反馈和再修改 → 验证工具是否有用。**

### 1. 建立可以检查、也可以修改的打浦桥现状

已有基础：config 的站点是 dapuqiao；common.py 支持街道边界裁切、建筑轮廓和高度、用途等数据；已有情景与三维展示流程。

需要补齐：

- 每栋建筑、地块和街段有稳定编号，修改和拆分后能找到原对象。当前缓存的 bid 按记录顺序创建，to_recs 又没有保留它，不适合长期关联意见和版本。
- 保存每项数据的来源、时间与是否经过人工核对。AI 解译高度、用途判断、产权资料不是同一类证据。
- 遗产、居民入口、通行路线等必须来自对应资料或现场核查，不能根据建筑大小或数据顺序推断。
- 保存独立的现状版本，拟议修改不能覆盖原始身份和属性。

关键问题：当前 assign_stakeholder 根据 EULUC、Function、AOI 用途查表，将一栋建筑归到一类主体。这能作为初步分析假设，但“商业建筑”不等于“开发者实际拥有”，“住宅”也不等于只与居民有关。保持三类主体，同时允许一栋楼关联多类主体，分别记录使用、管理、开发利益和证据；无法确认时明确标为假设。

输出：一份可以回答“这个对象是什么、资料从哪里来、哪些属性确定、哪些仍待确认”的现状模型。

### 2. 让三类主体表达具体要求

建议同时支持全区要求和指定地点的要求：例如希望保留哪些居住功能、在哪些区域增加容量、哪些公共服务或通行联系需要改善。用户可以选对象、点地图、填简短表单或写意见，不要求其先理解 FAR 等术语。

三类主体只是组织参与的方式，不代表同一类人的意见完全相同。应记录原话、位置、提出者类别、优先程度和理由，也保留同一群体内部的不同意见。

真实用户测试时记录参与者背景；如果由学生扮演三种角色，则只能称为模拟参与任务。不能把三种预设配方运行一遍就称为公众协商。

可尝试：让大语言模型把文字整理成“对象、要求、原因、待确认信息”。必须保留原文并让提出者确认；模型不自动决定保护身份、真实产权或规划底线。先用表单与人工整理跑通，再判断是否需要自动化。

### 3. 把要求变成有依据、可以解释的规则——论文核心之一

现在的问题不只是权重怎么选，而是两次转换缺少充分依据：**建筑用途到主体关系；主体诉求到空间操作。** 应分别检查，不能用前一步的角色标签代替后一步真实收集的需求。

每条规则至少回答六件事：谁提出、针对哪里、希望改变什么、用什么量检查、什么条件不能突破、依据是什么。

| 诉求例子，需由参与者确认 | 可以检查的空间要求 | 可能执行的修改 | 不能据此直接推断 |
|---|---|---|---|
| 保留现有居住功能 | 指定区域住宅面积或住宅单元保留情况 | 限制用途转换、限定可改对象 | 保留住宅面积不等于原居民一定留下 |
| 增加可开发容量 | 指定可更新对象新增楼面面积、允许高度 | 加层、局部重组或用途调整 | 容量增加不等于收益增加 |
| 改善公共空间 | 可进入的公共空间面积、与道路或入口的连通关系 | 开放空间、调整地块边界、补充连接 | 建筑缩小留下的空地不自动成为公共空间 |
| 保留历史环境 | 已确认对象及其允许改变的属性 | 按对象和属性保护、限制周边变化 | 单凭面积小不能认定历史价值 |

规则分成三种，界面上说清楚：

- **必须遵守的条件：** 来自已核实规定、场地边界或明确的研究约束，不能被提高另一方权重抵消。
- **可以协商的目标：** 可以讨论程度和取舍，需记录谁希望优先满足什么。
- **暂时采用的假设：** 缺少证据，允许试算，但结果必须标明依赖该假设。

权重只应表达目标之间的取舍，不应直接表示“哪个主体的楼应变高”。先统一指标单位或合理尺度，避免数值大的指标天然占优势；记录权重来源，试几个合理范围，观察结论是否稳定。

条件无法同时满足时，返回“哪些要求冲突、哪些对象导致冲突”，不要偷偷放松保护要求。若几种方案各有优势，可以并列交给参与者选择。

### 4. 让空间操作做它声称会做的事——论文核心之二

“算子”可以理解为一种明确的修改动作，例如保留、加层、改变用途、细分经营空间或开放通道。每种动作都要写清：什么情况下能用、允许改变什么、绝不能改变什么、完成后检查什么。

| 当前代码中的问题 | 框架中应规定的改法 |
|---|---|
| _copy_with_tags 按面积与序号添加 heritage、resident_gate 等标签 | 用已核实图层或显式研究假设代替；数据重新排序不能改变事实标签 |
| micro_lease 将整栋轮廓切成小块并重新设置高度 | 区分建筑、楼层和经营单元。若研究内部/首层细分，外壳应保持；若真的拆建，另立拆建动作并核算面积损失 |
| 小单元被标为 affordable_micro | 只能表示拟议低租金用途；没有租金、成本或经营数据，不能证明它可负担 |
| frontage_quota 用场地中轴代替道路，并按对象数分配配额 | 使用真实街网和街段，明确配额按长度、面积还是单元数计算；纳入冻结对象后重新检查是否达标 |
| 修改用途同时改 sh，后续又按 sh 补事实标签 | 原始主体关联、拟议用途、保护属性分别保存，功能变化不能自动变成产权或身份变化 |
| crowd_valve 没有真正使用路线与客流数据，只依据阈值参数缩建筑 | 有数据时连接路线网络、客流输入与明确的判断；无数据时称为设定的高峰情景，不能宣称拥挤预测 |
| night_reversion 没有按实际时刻判断，却缩轮廓和改高度 | 夜间开放、停业和占用变化用时间状态表达；永久几何变化单独处理 |
| 高度守恒模式不读取 cap_m，最低高度裁切又可能改变总量 | 把总量、上下限一起求解；求解后独立检查，不靠裁切补救 |
| apply_regime 顺序执行，没有统一的修改后检查 | 每一步检查几何有效、范围、重叠、保护条件、指标与编号；最终再查一次全部约束；失败时返回原因或回退 |

一个已做的小检查：两栋均为 100 平方米、10 米高，权重设为 10 与 1，并给第一栋 12 米上限。当前 conserve 函数得到约 18.18 米与 3 米，上限未生效，面积×高度总量从 2000 变成约 2118.18。**这是人工构造的诊断例子，不是打浦桥实测结果**，说明“守恒”“高度限制”需要实际检查。

固定随机种子可以帮助重复运行，但不证明动作合理。还要检查输入排序、随机种子及算子执行顺序改变时结果怎样变化；有必要的先后关系应明确固定，而不是要求所有动作都可以任意交换。

### 5. 比较结果，并允许再修改

整区总览用来查看更新强度和空间分布；街段、地块与建筑视图用来解释具体代价。局部交互不会缩小研究尺度：每次局部修改后，仍重新检查全区总量与相关网络影响。

至少展示：现状与方案、哪些对象改变、为什么改、三类主体相关的目标完成情况、未满足的条件。总区平均值不能掩盖某一片区集中了全部拆改或服务损失。

C6 的同视点切换可直接借鉴。当前 build_canvas.py 已有预生成方案切换、保存视角和导出；它主要是浏览入口。要成为编辑工具，需增加点选对象、修改参数后重新计算、保存与撤销、返回失败原因等动作。已有 _scenario_sequences 可承接过程回看。

每个方案保存父方案、提出者、规则版本、数据版本、参数及对象变化。参与者可以提出反方案；同一对象的相互冲突修改要明确提示，不自动覆盖。选择结果也要记录未解决的反对理由，不声称所有人已经达成共识。

AI 效果图可以辅助讨论，但形态、面积和变化记录应来自同一份几何模型；模型没改的建筑不应在效果图中被当成真实变化。

### 6. 检查“空间算对了”和“人用得上了”

两方面分别评估：

| 检查什么 | 建议如何做 |
|---|---|
| 规则有没有依据 | 对关键规则列出资料来源、专家检查和参与者确认结果；报告无法覆盖的诉求 |
| 动作有没有算对 | 检查保护对象、上下限、总量、几何重叠、道路连接、面积口径与可重复性 |
| 结论是否依赖随意参数 | 在合理范围内改变权重、数据误差和种子；报告哪些结论稳定、哪些容易翻转 |
| 不同主体是否真有不同考虑 | 使用同一场地和任务，记录三类主体的要求、理由和取舍；保留各类内部差异 |
| 工具有没有帮助表达和理解 | 比较现有浏览方式与新工具完成同一任务的情况：需求有没有表达准确、影响有没有看懂、能否提出有效修改 |
| 新映射是否比旧规则更可信 | 固定数据与参与任务，比较当前直接按主体权重改形态和改进后的规则流程；检查规则符合度及参与者对结果的确认 |
| 整区尺度是否能用 | 实测首次加载、一次编辑反馈时间、全区检查耗时；明确样本量和使用设备 |

当前 measure.py 主要量测 FAR、覆盖率、高度、粒度等，需补与具体诉求对应的指标。建筑栋数与经营单元数分开；楼面面积估计说明层高假设；净地块容积率与全区平均强度分开。公共空间、居民留居、商业活力不能仅由建筑空隙、住宅体量和商业标签推断。

用户实验不必同时证明所有功能。可先比较旧浏览流程与新编辑流程；若进一步研究“显示修改原因”有没有用，再增加能编辑但不显示原因的对照条件。真实三类代表难以招募时，诚实报告模拟任务的范围。先做形成性测试修正明显问题，再设计正式比较，样本量按研究问题与可行性说明。

## 四、哪些技术值得尝试

技术是用来解决上面的问题，不是为了把工具名字都放进论文。以下是我们的实现建议，不代表参考论文都采用了这些技术。

| 优先程度 | 技术 | 解决什么 | 使用前提与限度 |
|---|---|---|---|
| 必做 | 结构化规则表、独立校验器、版本记录 | 规则讲得清、动作可检查、修改可回看 | 先能逐条说清规则，不必先训练模型 |
| 必做 | GeoPandas / Shapely 的空间查询与几何检查 | 找到受影响对象，检查越界、重叠和几何错误 | 几何有效不等于满足规划、安全和通行要求，后者需另写检查 |
| 优先尝试 | 有约束的优化求解 | 同时满足总量、限高、用途配额等，而不靠操作后硬裁切 | 对固定候选动作的选择和线性配额可先试 MILP；自由几何与非线性条件不能直接套线性求解器 |
| 优先尝试 | 路网分析 | 检查入口、服务和公共空间之间是否连得通 | NetworkX 可做最短路径；需要真实可通行网络，最短路径本身不预测客流 |
| 根据需要 | 多目标方案搜索 | 给出不同取舍的候选，而不是一个加权总分掩盖差异 | 明确每个目标的意义，保留各群体代价；避免宣称算法替人作最终决定 |
| 根据需要 | 文本聚类或大语言模型辅助整理意见 | 帮助处理较多反馈 | 保留原话与少数意见，人工确认，不能按出现频率决定合理性 |
| 后续再做 | 查找带来源的知识资料，辅助解释规则 | 给解释附上证据 | 检索到相关文字不等于规则适用；规范版本和适用范围仍需核查 |
| 性能确实不足再做 | 预计算、缓存、只重算受影响部分 | 在全区模型上实现较快反馈 | 全区约束和路网变化仍需完整检查；不能因局部缓存漏算远处影响 |
| 数据充分后再考虑 | 用简化预测模型估计较慢的环境指标 | 加快多方案探索 | 先有可靠训练标签和留出验证，标明预测误差；它不负责生成利益诉求 |

MILP、路网与几何检查分别可参考 [SciPy milp](https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.milp.html)、[NetworkX 最短路径](https://networkx.org/documentation/stable/reference/algorithms/shortest_paths.html)、[Shapely is_valid](https://shapely.readthedocs.io/en/stable/reference/shapely.is_valid.html) 官方文档。它们提供计算能力，不自动提供城市更新规则的依据。

先把“可靠底模＋可解释规则＋严格动作＋真实反馈”完成，再判断是否需要图神经网络、扩散模型或多代理。没有训练资料时，这些模型不会自动使映射更严谨。

## 五、文章可以直接按这个结构写

| 章节 | 用人话说这一章要回答什么 | 建议放的证据或图表 |
|---|---|---|
| 1 引言 | 打浦桥更新中，不同人的要求为什么难以进入空间方案？ | 一个整区更新任务，说明表达与推演之间的困难 |
| 2 相关研究 | 别人已经解决了什么，我们具体补哪一步？ | 按公众表达、空间生成、方案比较三类比较上述文献，不只罗列作者 |
| 3 场地、主体与数据 | 研究哪片地方、谁参与、数据可信吗？ | 全区范围、数据来源、主体关联依据和缺失分布 |
| 4 方法与工具 | 一条诉求如何一步步变成可修改的方案？ | 总流程图、规则表、动作表、前后变化例子与交互界面 |
| 5 实验设计 | 怎样判断规则、结果和参与过程有用？ | 技术检查、参数变化实验、用户任务及对照方式 |
| 6 结果 | 实际算出了什么，用户实际完成了什么？ | 全区与分区指标、规则失败记录、用户结果；全部基于实际实验 |
| 7 讨论与结论 | 哪些贡献得到支持，哪些仍是假设？ | 数据误差、角色简化、参与代表性、效益指标边界及后续工作 |

摘要也可以沿用这个顺序压缩：现实困难 → 明确工具任务 → 数据、需求和规则流程 → 技术与用户验证 → 实际发现 → 有限度的贡献。实验未完成前，结果写待验证目标，不提前写“显著提高参与、公平或韧性”。

建议的贡献表述：**提出并验证一种面向打浦桥整区更新的参与式设计流程，将居民、开发者和政府提出的要求转成有来源、可检查的空间规则，使用户可以修改方案、比较不同取舍，并回看自己的意见如何影响空间变化。** “验证”一词应在相关实验实际完成后使用。

## 六、先改什么，后改什么

1. **先补可信基础：** 主体关联的依据、真实标签、稳定编号、指标口径；修正限高和守恒检查。
2. **再跑通一条完整流程：** 围绕整区居住保留、开发容量与公共空间取舍，完成需求输入、规则确认、空间修改、结果解释和再修改。全区尺度不变，但先减少没有数据支持的动作。
3. **再验证与比较：** 技术检查、参数敏感性和三类主体的使用任务。
4. **最后扩展：** 有对应数据后再加入客流、时段、租金或更复杂生成技术；否则保留为明确标注的情景假设。
